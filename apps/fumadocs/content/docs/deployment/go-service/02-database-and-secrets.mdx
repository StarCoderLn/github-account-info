## 本阶段目标

在启动 Go Task 前创建 `profile_introduction` 表，并把 production、preview 两套连接串安全地放入 Secrets Manager。Go runtime 不自动执行 migration，避免多个 Task 并发启动时争抢数据库结构变更。

## 1. 明确数据库所有权

- `packages/db/src/migrations/` 是 production schema 唯一事实来源。
- Node/Drizzle 负责 migration；Go 只消费已经存在的表。
- production 使用 `public` schema。
- preview 使用独立 database，再按 PR 创建 `pr_<number>` schema。

不要在 Go 中复制一套 production migration，否则两种 ORM 会逐渐产生不同的结构认知。

## 2. 建立 production SSM 隧道

在终端 1 执行，替换实例和 RDS hostname：

```bash
aws ssm start-session \
  --region us-east-2 \
  --target <BASTION_INSTANCE_ID> \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters '{"host":["<RDS_HOSTNAME>"],"portNumber":["5432"],"localPortNumber":["15432"]}'
```

保持终端不退出。这个过程不需要给 EC2 开放 SSH 22；SSM Agent 使用出站 443 建立会话。

## 3. 执行 repository-owned migration

在终端 2 从仓库根目录运行：

```bash
bash infra/scripts/migrate-production-via-tunnel.sh
```

脚本会隐藏读取 production `DATABASE_URL`，并做以下保护：

1. 拒绝空值和非 PostgreSQL URL。
2. 校验目标 database 必须是 `github_account_info`。
3. 只在 migration 子进程中把 hostname 改为 `127.0.0.1:15432`。
4. 加入 `sslmode=require&uselibpqcompat=true`。
5. migration 结束后清空 shell 变量。

<Callout type="warn" title="不要使用 bash -x">
  脚本处理包含密码的连接串。`bash -x` 会破坏隐藏输入和不打印 Secret 的边界。
</Callout>

SSM 隧道把地址改成 localhost，localhost 无法匹配 RDS 证书 hostname。`uselibpqcompat=true` 让 `sslmode=require` 保持“强制加密但不做 hostname verify”的 libpq 语义，仅用于本地隧道 migration。ECS 直连真实 RDS hostname 时仍必须完整校验证书。

## 4. 只读验证 migration

使用数据库客户端查询元数据，不查询用户资料：

```sql
SELECT to_regclass('public.profile_introduction');

SELECT id, hash, created_at
FROM drizzle.__drizzle_migrations
ORDER BY created_at DESC;
```

第一条应返回 `profile_introduction`；第二条应包含最新 migration journal。若表不存在，不要继续创建 ECS Service，因为 Task 的启动 ping 不能证明业务表已经准备完成。

## 5. 创建 production Secret

在 AWS Console 打开 Secrets Manager：

1. 选择 **Store a new secret**。
2. 选择 **Other type of secret**。
3. 将完整 production `DATABASE_URL` 作为整个 SecretString 保存。
4. 名称使用 `github-account-info/production/database-url`。
5. 不要在 description、tag 或 CloudFormation 参数中复制 Secret value。
6. 记录 Secret ARN，后续 `go-iam.yaml` 只接收 ARN。

若使用默认 `aws/secretsmanager` KMS key，IAM 参数中的自定义 KMS ARN留空；若使用 customer-managed key，Execution Role 还需要受 `kms:ViaService` 限制的 `kms:Decrypt`。

## 6. 创建 preview database 和用户

使用管理员连接 RDS，在 `psql` 里交互输入随机密码：

```sql
\prompt 'Preview database password: ' preview_password
CREATE ROLE github_account_info_preview LOGIN PASSWORD :'preview_password';
CREATE DATABASE github_account_info_preview OWNER github_account_info_preview;
\unset preview_password
```

不要给 preview 用户 production `public` schema 或表权限。验证：

```sql
SELECT
  has_table_privilege(
    'github_account_info_preview',
    'public.github_account',
    'SELECT'
  ) AS can_read_accounts,
  has_table_privilege(
    'github_account_info_preview',
    'public.profile_introduction',
    'SELECT'
  ) AS can_read_introductions;
```

两个结果都应为 `false`。

## 7. 创建 preview Secret

在 Secrets Manager 新建：

```text
Name: github-account-info/preview/database-url
Database: github_account_info_preview
Username: github_account_info_preview
```

Preview Secret 必须是独立 ARN。Preview ECS Execution Role 只能读取它，不能读取 production Secret。

## 8. 理解 PR schema 边界

每个 PR 的 `DB_SCHEMA` 只能由可信 PR number 构造，例如 `pr_123`。它不是 HTTP 输入。`preview-db` 一次性任务负责创建 schema、应用结构和写入虚构的 `preview-user` seed。

同一 preview database credential 理论上能访问其他 preview schema，因此这是可信协作者之间的功能隔离，不是恶意多租户安全边界。外部 PR 必须经过 CodeBuild approval 后才允许执行。

## 本阶段完成标准

- [ ] production migration journal 已更新。
- [ ] `public.profile_introduction` 存在。
- [ ] production Secret 只保存于 Secrets Manager，已记录 ARN 而非值。
- [ ] preview database 与 preview 用户已创建。
- [ ] preview 用户不能读取 production 表。
- [ ] preview Secret 使用独立 ARN和独立 database。
